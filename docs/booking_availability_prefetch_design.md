# 予約可能時間の先行取得設計

## 背景

現在の予約画面は、メニュー一覧と予約可能時間を別々に取得している。

- メニュー一覧は `/booking` の初期表示時に Firestore から取得する。
- 予約可能時間は「日時」ステップへ進んだ後に Cloud Functions の
  `getReservationAvailability` を初めて呼び出す。

`getReservationAvailability` は第1世代の Callable Function で、`minInstances`
は設定されていない。このため、インスタンスが停止している場合は「日時」画面へ
進んだ直後にコールドスタート時間が表面化する構成になっている。

なお、実測ログなしでは待ち時間の全てをコールドスタートとは断定できない。
Firestore の5クエリやネットワーク、Firebase Authトークン取得も計測対象とする。

## 目的

- 「日時」ステップで予約可能時間が表示されるまでの待ち時間を短縮する。
- メニュー一覧が表示されるまでの時間を悪化させない。
- 同じ期間への二重リクエストを防ぐ。
- 古い予約枠を予約可能として扱い続けない。

## 採用方針

### 1. メニュー表示完了後にのみ先行取得する

初期表示では、現状どおり `loadBookingMenus()` だけを優先して実行する。
`catalog` がセットされ、認証済みユーザーが確定した後に、当週7日分の予約枠を
低優先度で先行取得する。

開始条件は次のとおりとする。

1. `catalog` が存在する。
2. `currentStep === 0` である。
3. `currentUser` が存在する（APIが認証必須のため）。
4. 対象期間が未取得かつ未取得中である。

開始タイミングには `requestIdleCallback` を使い、未対応ブラウザでは短い
`setTimeout` にフォールバックする。Reactの `catalog` 更新後の effect から
スケジュールするため、メニューの初回取得・初回描画を待たせない。

加えて、ユーザーがメニューを選択した時点ではアイドル待ちを解除し、同じ期間の
先行取得を即時に開始する。これにより、ユーザーが一覧をすぐ操作した場合にも、
「日時へ進む」ボタンを押すまでの時間をウォームアップに使える。

電話予約専用メニューでは日時画面へ進まないため、選択時の即時取得は行わない。

### 2. 進行中Promiseと結果を期間単位で共有する

予約枠取得を管理する小さなクライアント側ストアを
`src/features/booking/booking-availability-prefetch.ts` に設ける。

期間キーは `from.toISOString()` と `until.toISOString()` の組み合わせとする。
各キーについて以下を保持する。

- 進行中の `Promise<BookingAvailability>`
- 成功結果
- 取得完了時刻

`prefetchBookingAvailability(range)` と
`getBookingAvailability(range)` は同じ内部処理を使用する。すでに取得中なら同じ
Promiseを返し、完了済みで有効期限内なら結果を返す。これにより、先行取得中に
日時画面へ進んでも二重に Callable Function を起動しない。

エラー結果（`availabilityIsLive: false`）はキャッシュしない。次の明示的な取得で
再試行できるようにする。

### 3. 日時画面で鮮度を判定する

先行取得結果の有効期限は30秒とする。

- 30秒以内: 先行取得結果を即時利用する。
- 30秒超過: 新しく取得してから予約枠を表示する。

古い結果でも関数のウォームアップ自体は済んでいる可能性が高いため、再取得は
コールドスタートの影響を受けにくい。予約確定時のサーバー側重複検証は今まで
どおり必須であり、先行取得結果を確定可否の根拠にはしない。

### 4. 翌週以降は現状どおり操作時に取得する

初期先行取得は最初に表示する当週7日分だけに限定する。翌週をまとめて取得すると
不要なFirestore読み取りが増えるため、「次の一週間」を押した時点で取得する。
期間単位ストアにより、前の週へ戻った場合は有効期限内の結果を再利用できる。

## 処理フロー

```text
/bookingを表示
  ├─ loadBookingMenus() ──> catalog更新 ──> メニュー一覧を描画
  └─ 認証状態を確定
              │
              └─ 描画後のidle時間
                    └─ 当週availabilityを先行取得
                          ├─ 取得中Promiseを保持
                          └─ 成功結果と取得時刻を保持

メニュー選択
  └─ 未開始ならavailability取得を即時開始

「日時へ進む」
  ├─ 取得済み・30秒以内 ──> 即時表示
  ├─ 取得中             ──> 同じPromiseを待つ
  └─ 未取得・期限切れ    ──> 新規取得して表示
```

## 主な変更箇所

### `src/features/booking/booking-data.ts`

- `loadBookingAvailability` はネットワークアクセスの低レベル関数として維持する。
- 失敗を `unavailableBookingAvailability()` に変換する現在の契約も維持する。

### `src/features/booking/booking-availability-prefetch.ts`（新規）

- 期間単位のPromise重複排除を実装する。
- 成功結果の30秒TTLを実装する。
- テスト用に時刻注入とストア初期化手段を用意する。

### `src/features/booking/components/booking-flow.tsx`

- メニュー描画後かつ認証後に、アイドルコールバックで当週を先行取得する effect を追加する。
- `chooseMenu` で、通常メニューの場合は同じ先行取得を即時開始する。
- 日時ステップの effect はストア経由の取得へ切り替える。
- effect cleanup 後のstate更新を防ぐ既存の `isActive` 制御は維持する。
- 先行取得だけでは `isAvailabilityLoading` を変更しない。メニュー画面にローディング表示を追加しない。

## 失敗時の挙動

- 先行取得に失敗してもメニュー画面にはエラーを表示しない。
- 日時画面へ進んだ時点で失敗中または失敗済みなら再取得する。
- 日時画面での取得にも失敗した場合は、現在と同じ「空き状況を確認できません」を表示する。
- コンポーネント破棄時はアイドルコールバックをキャンセルする。Callable Function自体は
  AbortSignalに対応していないため通信の中断は行わず、結果だけストアに保持する。

## 検証計画

### 自動テスト

- 同じ期間を同時に2回要求しても `loadBookingAvailability` が1回だけ呼ばれる。
- 30秒以内は結果を再利用する。
- 30秒経過後は再取得する。
- 失敗結果は再利用しない。
- 異なる週は別リクエストになる。

### ブラウザ確認

- 初回アクセスで、メニュー一覧の表示後に予約枠リクエストが始まる。
- メニュー一覧表示前には予約枠リクエストが始まらない。
- 先行取得中に日時へ進んでもネットワークリクエストが1本のままである。
- 先行取得完了後は日時画面の予約枠が直ちに表示される。
- 未ログイン時には認証必須APIを呼ばず、ログイン復帰後に取得できる。
- 電話予約専用メニューでは選択を理由とする即時取得が発生しない。

### パフォーマンス計測

変更前後で本番相当環境を各10回以上計測する。

- `booking_menu_ready_ms`: ページ開始からメニュー一覧描画まで
- `availability_request_ms`: Callable Functionの通信時間
- `datetime_slots_ready_ms`: 「日時へ進む」操作から予約枠表示まで
- Cloud Functionsログ上の実行時間とインスタンス起動状況

受け入れ条件は、`booking_menu_ready_ms` の中央値およびp95が変更前より有意に悪化せず、
先行取得完了ケースの `datetime_slots_ready_ms` が体感上ほぼ即時になることとする。

## 今回の対象外

- Cloud Functionsの `minInstances` 設定変更
- 予約枠APIのクエリ統合やFirestoreデータモデル変更
- 複数ユーザー間で共有するCDNキャッシュ

`minInstances` はコールドスタートを直接抑える別案だが、常時起動コストが発生する。
先行取得後の実測でも遅い場合に、API処理時間の最適化と合わせて次段階で検討する。
